# 晚辅与专项课量化反馈 Agent 产品设计

日期：2026-09-08  
状态：已确认，待实施计划

## 1. 产品目标

在现有教学反馈数据采集 Demo 上增加学生成长档案和周报生成能力，把老师已经录入的晚辅、专项课结构化反馈转化为可追溯、可审核、可复制的家长周报草稿。

第一阶段继续验证两个问题：

1. 老师是否愿意持续录入精简、结构化的学生反馈。
2. 这些反馈能否稳定生成有事实依据、可直接修改使用的周报草稿。

系统不自动联系家长。所有周报必须经过老师审核，AI 不得修改原始反馈。

## 2. MVP 边界

### 2.1 包含

- 继续使用“班级 → 课程场次 → 学生反馈”的现有结构。
- 从现有晚辅三项评分、专项两项评分、指标勾选、老师备注和历史变化构建学生成长档案。
- 展示学生基础信息、近期评分、趋势、高频进步项、高频薄弱项、近期备注和历史周报。
- 按班级和周期为单个学生或整班生成周报草稿。
- 支持离线规则模板和可替换 AI 模型两种生成模式。
- AI 不可用、输出不合规或未配置时自动退回规则模板。
- 支持老师编辑、定稿和复制周报。
- 保存每份周报所引用的原始反馈记录。

### 2.2 不包含

- 机构、校区或多租户层级。
- 独立的成绩、作业、家庭画像、家长类型和心理画像数据表。
- 自动向微信、短信或其他渠道发送内容。
- 完整六 Agent 编排、独立任务队列或知识图谱。
- 独立 RAG 知识库。
- 入学测评业务记录、月度汇总和自动学习方案。

## 3. 总体架构

```text
老师
  → 班级
  → 课程场次
  → 结构化学生反馈
  → 学生档案聚合视图
  → 周报草稿（规则模板 / AI）
  → 老师审核、定稿、复制
```

现有 FastAPI、Jinja2、SQLAlchemy 和 SQLite 架构保持不变。新增档案查询与周报模块，不建立新的学生画像事实源；学生档案由现有业务数据实时聚合。

## 4. 数据模型

### 4.1 现有核心关系

```text
class
  ├─ enrollment → student
  └─ class_session
       ├─ daily_feedback → daily_feedback_indicator → indicator
       └─ special_feedback → special_feedback_indicator → indicator
```

### 4.2 weekly_report

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| report_id | TEXT | PK | 周报业务编号 |
| student_id | TEXT | FK→student，非空 | 学生 |
| class_id | TEXT | FK→class，非空 | 班级 |
| teacher_id | TEXT | FK→teacher，非空 | 创建或负责审核的老师 |
| period_start | TEXT | 非空 | 周期开始日期，YYYY-MM-DD |
| period_end | TEXT | 非空 | 周期结束日期，YYYY-MM-DD |
| generation_mode | TEXT | template / ai | 实际生成模式；AI 回退后记录 template |
| status | TEXT | draft / finalized | 草稿或定稿 |
| summary | TEXT | 非空 | 整体总结 |
| strengths | TEXT | 非空 | JSON 字符串数组，主要进步 |
| concerns | TEXT | 非空 | JSON 字符串数组，待改善问题 |
| suggestions | TEXT | 非空 | JSON 字符串数组，下阶段建议 |
| generation_note | TEXT | 可空 | 回退原因或生成说明，不展示给家长 |
| created_at | TEXT | 非空 | 创建时间 |
| updated_at | TEXT | 非空 | 更新时间 |
| finalized_at | TEXT | 可空 | 定稿时间 |

约束：`period_end >= period_start`；同一学生、班级和周期允许保留多份草稿，以支持重新生成，但一次只有一份定稿。应用层在定稿事务中保证这一规则。

### 4.3 weekly_report_source

| 字段 | 类型 | 约束 | 含义 |
|---|---|---|---|
| report_id | TEXT | FK→weekly_report，PK 部分 | 周报 |
| feedback_type | TEXT | daily / special，PK 部分 | 来源反馈类型 |
| feedback_id | TEXT | PK 部分 | 来源反馈业务编号 |

由于 SQLite 无法让一个外键根据类型指向两张反馈表，`feedback_id` 的存在性由服务层在同一事务中校验。来源关联在周报生成时固定，不因后续反馈编辑自动改变。

### 4.4 学生成长档案视图

学生成长档案不是新表，而是以下数据的聚合结果：

- 基础信息：姓名、年级、九阶阶段、晚辅档位、有效班级。
- 近期表现：晚辅知识、习惯、心态评分；专项技能、习惯评分。
- 趋势：指定周期或最近 4–8 周的首末评分和变化。
- 高频指标：按分类统计进步项和薄弱项，按次数及指标顺序稳定排序。
- 老师观察：最近的有效反馈备注。
- 历史周报：草稿和定稿列表。

作废反馈不参与档案统计和新周报生成。

## 5. 页面与操作流程

### 5.1 导航

```text
今日填写 | 历史记录 | 学生档案 | 周报中心 | 基础信息
```

### 5.2 学生档案页

- 按班级和学生筛选，普通老师只能看到自己负责班级内的学生。
- 顶部展示学生基础信息。
- 展示最近 4–8 周评分趋势；首期使用本地 CSS/SVG 或表格，不加载外部图表库。
- 展示高频进步项、薄弱项和近期备注。
- 分析项可链接回对应原始反馈。
- 展示该学生的历史周报。

### 5.3 周报中心

1. 老师选择班级、开始日期和结束日期。
2. 系统列出有效学生及每人的有效反馈数量。
3. 反馈不足时显示提示；反馈数量大于零仍允许生成。
4. 无有效反馈的学生不可生成，并显示原因。
5. 老师选择单个学生或整班，选择“规则模板”或“AI”，生成草稿。
6. AI 未配置或失败时自动生成规则草稿，并在后台生成说明中记录回退原因。
7. 老师在详情页修改草稿并定稿。
8. 定稿后仍可查看来源记录并复制正文；首期不直接发送。

批量生成逐个学生独立执行。某个学生失败不会回滚其他学生已经成功生成的草稿。

## 6. 周报生成工作流

```text
选择学生与周期
  → 查询有效反馈
  → 计算评分变化和指标频次
  → 构建结构化周报上下文
  → 规则模板或 AI 生成
  → 校验输出
  → 固定来源并保存草稿
  → 老师编辑、定稿、复制
```

### 6.1 ReportContextBuilder

只负责读取、授权校验和聚合，不生成自然语言。输出至少包含：学生基础信息、周期、反馈数量、评分首末值及变化、高频进步项、高频薄弱项、近期备注和来源反馈编号。

相同输入必须产生稳定排序的上下文，便于测试和追溯。

### 6.2 TemplateReportGenerator

离线默认生成器。使用固定中文模板生成整体总结、主要进步、待改善问题和下阶段建议。没有某类数据时明确省略该结论，不猜测缺失信息。

### 6.3 AIReportGenerator

通过可替换接口接收与模板生成器相同的结构化上下文。模型名称、地址和密钥通过环境变量配置，不写入代码或数据库。

AI 必须返回：

```json
{
  "summary": "本周整体表现",
  "strengths": ["明确进步1", "明确进步2"],
  "concerns": ["需要改善的问题"],
  "suggestions": ["下周可执行建议"]
}
```

### 6.4 ReportValidator

- 校验必需字段和字段类型。
- 限制各部分长度和列表数量。
- 校验文案中出现的明确数字可由上下文支持。
- 拒绝未经记录的成绩、家庭情况和心理诊断。
- 把“懒惰”“粗心型”等人格标签改为或拒绝为可观察行为描述。
- 校验失败、接口异常、超时或缺少配置时调用模板生成器。

## 7. 权限和数据安全

- 管理员与校区负责人沿用现有全局数据权限。
- 普通老师只能访问自己负责班级的学生档案、自己可见的反馈及其周报。
- 周报详情和来源链接执行与列表一致的服务端权限校验，不能只依赖页面隐藏。
- AI 仅接收生成周报所需的最小结构化信息；首期不传递家庭信息。
- 原始反馈是事实源，周报是派生内容。编辑周报不能反向修改反馈。
- 反馈后续被作废时，旧周报继续保留，并显示“引用记录状态已变化”。

## 8. 技术实现

- 后端：FastAPI。
- 页面：Jinja2 + 少量原生 JavaScript。
- 持久化：SQLAlchemy + SQLite。
- 趋势呈现：本地 CSS/SVG 或表格，不引入 CDN。
- 生成接口：同步应用服务接口；首期不引入任务队列。
- 模型配置：环境变量；未配置时模板模式仍完整可用。
- 本地知识：复用九阶、指标和测评参考字典；首期不建设独立 RAG。

建议新增模块：

```text
app/profiles/routes.py       学生档案页面
app/profiles/service.py      档案聚合查询
app/reports/models.py        周报与来源模型
app/reports/service.py       生命周期、批量生成和定稿
app/reports/context.py       周报上下文构建
app/reports/generators.py    模板与 AI 生成接口
app/reports/validation.py    输出校验与回退规则
app/reports/routes.py        周报中心与详情页面
app/templates/profiles/      学生档案模板
app/templates/reports/       周报页面模板
```

## 9. 测试策略

- 周期边界、评分首末值和变化计算。
- 高频指标排序、并列和空数据处理。
- 作废反馈排除。
- 普通老师的数据范围隔离。
- 规则模板的确定性输出。
- AI 输出结构校验、超时和失败回退。
- 周报来源固定及状态变化提示。
- 批量生成部分失败隔离。
- 草稿编辑、单一定稿约束和复制页面。
- 从反馈录入到档案聚合、周报生成和定稿的端到端验收。

所有新行为遵循测试先行。AI 测试使用实现同一生成接口的本地假模型，不调用外部网络。

## 10. 实施顺序

1. 学生档案聚合服务和档案页面。
2. 周报数据表、来源关联和数据库升级。
3. 规则模板、周报中心和批量生成。
4. AI 生成接口、输出校验和自动回退。
5. 老师试用，记录生成耗时、修改比例、常见修改点和最终采用率。

是否增加成绩、作业、家长画像、RAG 和更复杂的 Agent 编排，由第一阶段试用数据决定。

## 11. 完成标准

- 老师能从班级进入学生档案并查看现有反馈形成的趋势与摘要。
- 老师能按周期为单个学生或整班生成周报草稿。
- 没有模型配置时规则模板可完整运行。
- AI 失败或输出不合规时自动回退且留下说明。
- 每份周报可追溯到具体反馈记录。
- 老师能够编辑、定稿和复制，但系统不会自动发送。
- 权限范围与现有应用一致。
- 新增和既有自动化测试全部通过。
