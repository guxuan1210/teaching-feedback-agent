# 企业微信家庭沟通与学生图片归档设计

## 1. 目标

在现有 Teaching Agent 中增加一套以学生业务 ID 为中心的图片归档与家校沟通能力：

- 已绑定老师可在企业微信智能机器人私聊中发送图片，并把图片归档到指定学生。
- 图片上传消息优先读取同条消息里的学生 ID 或姓名；无法唯一识别时，由机器人追问确认。
- 每名学生可关联多位家长和多位老师；家长也可关联多个孩子。
- 普通微信家长通过企业微信“微信客服”入口和一次性邀请码完成身份绑定。
- 家长可查询自己孩子的反馈、周报和图片，并向机器人或负责老师提问。
- 机器人回复与老师回复必须明确标注真实回复者，全部消息统一留档。
- 图片先保存在本机受控目录，存储边界允许未来替换为腾讯云 COS 等对象存储。

## 2. 当前基础与平台边界

现有系统已经具备：

- 不可重复的 `student_id`、`teacher_id` 和班级/入班关系。
- 老师网页登录、数据范围控制和学生档案。
- 企业微信智能机器人 WebSocket 长连接、老师绑定、文本问答与会话复用。
- SQLite 数据库和本机 `data/` 数据目录。

当前企业微信智能机器人用于企业内部成员，普通微信家长不能作为内部成员直接私聊该机器人。因此采用双入口：

- 老师使用现有企业微信智能机器人。
- 家长使用企业微信“微信客服”入口。

两个入口在应用内部接入同一个学生关系、媒体和家庭会话领域。图片消息能力按企业微信智能机器人支持的单聊图片及图文混排消息设计；正式联调时以企业微信当前接口文档和测试企业的实际权限为准。

## 3. 方案选择

采用“统一会话中心 + 系统中转回复”。

家长消息先进入应用。机器人可以直接回复，也可以把问题转发给学生的负责老师。老师在现有智能机器人中确认并回复，应用再把老师消息发送至家长的微信客服会话。

不采用企业微信原生人工接待作为主要实现，因为原生接待难以统一控制学生归属、老师权限、回复者标签和完整审计。不采用网页专用客服工作台，因为老师需要继续在企业微信内工作。

## 4. 架构与组件

### 4.1 老师机器人适配器

扩展现有 `app.wecom` 网关，接收老师私聊中的图片和图文混排消息。适配器只负责解析渠道事件、下载媒体、发送确认或追问，不直接决定业务权限与归档规则。

### 4.2 家长微信客服适配器

新增微信客服渠道适配器，负责：

- 接收普通微信家长消息。
- 识别渠道外部联系人。
- 发送机器人或老师的回复和图片。
- 保存渠道消息 ID、发送状态和失败原因。

该适配器需要独立的企业微信企业凭据、微信客服账号配置，以及企业微信能够访问的回调地址或等价的安全接入方式。

### 4.3 学生关系服务

集中处理学生、家长、老师之间的关系和访问判断。其他组件不能仅凭姓名、渠道昵称或前端参数授予访问权限。

### 4.4 媒体服务

负责下载、解密、校验、落盘、读取和隔离删除图片。业务层只使用媒体服务返回的图片 ID 与元数据，不拼接任意文件路径。

### 4.5 家庭会话服务

统一保存家长消息、机器人回复和老师回复，负责回复者标注、转人工状态、老师路由和渠道发送状态。

### 4.6 网页管理与学生档案

管理员和校区负责人可维护学生家长关系、学生老师关系、生成或撤销邀请码并查看沟通记录。学生档案新增图片区；图片下载通过授权接口完成，不把媒体目录公开挂载为静态目录。

## 5. 数据模型

### 5.1 `guardian`

保存监护人主体：`guardian_id`、姓名、身份类型、状态、创建与更新时间。身份类型包括父亲、母亲和其他监护人。

### 5.2 `student_guardian`

保存学生与监护人的多对多关系，包含关系状态、建立时间和撤销时间。一个家长可关联多个孩子，一个学生可关联多位监护人。

### 5.3 `guardian_channel_binding`

保存家长渠道身份，至少包含渠道类型、企业微信客服外部联系人标识、`guardian_id`、绑定状态和绑定时间。渠道标识在同一渠道内唯一。

### 5.4 `guardian_invitation`

保存指定学生的一次性邀请码摘要、过期时间、允许使用次数、已使用次数、撤销时间、创建人和创建时间。数据库不保存邀请码明文。邀请码默认仅允许使用一次；管理员可为同一学生生成多个独立邀请码，供不同监护人绑定。

### 5.5 `student_teacher_assignment`

显式保存学生与老师的多对多关系，包含职责类型（主负责、任课、协同）、起止时间和状态。班级班主任关系同步为主负责关系；消息转交优先选择有效的主负责老师。

### 5.6 `student_image`

保存：

- 图片 ID、学生 ID、上传老师 ID。
- 企业微信原始消息 ID 和同一消息内的图片序号。
- 老师说明、MIME 类型、扩展名、文件大小和 SHA-256。
- 相对存储路径、状态、上传时间、软删除与隔离信息。

`原始消息 ID + 图片序号` 唯一，保证渠道重试不产生重复记录。每张图片只归属于一个学生。

### 5.7 `pending_media_assignment`

保存尚未确认学生归属的短期媒体任务，包括老师、原始消息、候选学生、临时文件、过期时间和状态。任务确认后转为正式图片；过期任务删除临时文件。

### 5.8 `family_conversation`

保存监护人、学生、当前负责老师、渠道会话标识、处理状态和最近活动时间。家长关联多个学生时，每个学生使用独立会话范围。

### 5.9 `family_message`

保存会话消息、方向、发送者类型、发送者 ID、正文、引用图片、渠道消息 ID、发送状态、失败原因和时间。发送者类型至少包括家长、机器人和老师。

## 6. 权限模型

- 老师必须完成现有企业微信账号绑定。
- 老师只有在 `student_teacher_assignment` 中存在当前有效关系时，才能为该学生上传、读取图片或回复家长。
- 管理员和校区负责人可管理全部关系与审计记录。
- 家长必须通过有效邀请码建立 `guardian_channel_binding` 和 `student_guardian` 关系。
- 家长只能读取有效关系内学生的数据；所有查询在服务端重新检查关系，不信任渠道传入的学生 ID。
- 解绑家长或停用老师立即撤销未来访问，但不删除历史记录。
- 机器人生成的回复始终标记为“机器人回复”；只有已授权老师亲自确认发送的内容才能标记为该老师回复。

## 7. 老师图片上传流程

1. 老师向智能机器人发送图文混排消息，例如“张三 S_xxx 今天作业订正”，并附一张或多张图片。
2. 系统先读取消息中的精确学生 ID；没有 ID 时，只在该老师当前有权限的学生中匹配姓名。
3. 唯一匹配后，媒体服务下载并解密图片，检查真实文件类型、大小和完整性，计算 SHA-256。
4. 文件先写入临时路径，校验通过后原子移动至正式目录，再提交数据库记录。
5. 机器人确认学生姓名、学生 ID、归档数量和说明。
6. 若消息未包含学生信息、姓名重名或无权限，则建立待确认任务并返回有权限的候选学生。
7. 老师选择学生后再次校验实时权限，再完成归档。
8. 待确认任务超时后清理临时文件，不进入学生档案。

纯图片消息沿用相同追问流程。图文消息中的非学生文字作为图片说明；学生 ID 和用于匹配的姓名不重复写入说明。

## 8. 本机存储设计

正式文件路径：

`data/student_media/{student_id}/{year}/{month}/{image_id}.{extension}`

规则：

- 首期接收 JPEG、PNG 和 WebP，默认单张上限 10 MB；限制通过配置调整。
- 文件扩展名由实际文件头和允许的 MIME 类型决定，不信任远端文件名。
- 使用系统生成的图片 ID 作为文件名，拒绝路径穿越。
- 下载、解密和校验在临时目录完成；只有文件和数据库都成功时才对业务可见。
- 媒体目录不作为公开静态目录挂载。
- 管理员软删除后，文件移入隔离区；恢复期结束后才能物理删除。
- SQLite 数据库和 `data/student_media` 必须作为同一个备份单元。
- 媒体服务通过存储接口访问文件，未来可在不改变业务调用方的情况下替换为对象存储。

## 9. 家长绑定与查询流程

1. 管理员在学生档案中生成限时一次性邀请码，并将明文码安全交给指定家长。
2. 家长通过微信客服入口发送邀请码。
3. 系统校验邀请码摘要、有效期、次数和学生状态，再让家长选择父亲、母亲或其他监护人。
4. 系统创建或复用监护人主体，建立渠道绑定和学生关系，并立即消耗邀请码。
5. 家长可以查询该学生的反馈、已定稿周报和图片。
6. 家长发送“看最近的图片”等请求时，系统返回日期、说明和上传老师标识，并通过微信客服渠道发送图片。
7. 一个家长绑定多个孩子时，未明确学生的请求先要求选择孩子；选择只作用于当前家庭会话范围。

邀请码不得用于改变已经绑定的渠道身份所代表的监护人。需要新增孩子时，在同一监护人下增加新的 `student_guardian` 关系。

## 10. 家长、机器人与老师沟通流程

1. 家长消息进入家庭会话并标记监护人身份。
2. 机器人能在权限范围内可靠回答时，发送带“【机器人回复】”前缀的答复。
3. 家长明确要求老师回复，或问题涉及个别判断、投诉、安全和其他敏感事项时，会话进入待老师处理状态。
4. 系统将学生、家长身份、问题、会话编号和必要上下文推送给主负责老师的智能机器人。
5. 老师通过交互按钮或“回复 会话编号 内容”确认发送。
6. 系统再次验证老师与学生的有效关系，然后通过微信客服向家长发送“【老师：姓名】内容”。
7. 每次接收、生成、确认和渠道发送均记录状态。发送失败保留为待重试或失败，不伪装成已送达。
8. 机器人不可代替老师署名。由模型生成但未经老师亲自编辑或确认的内容仍标记为机器人回复。

## 11. 网页功能

学生档案新增：

- 图片缩略图、上传时间、说明和上传老师。
- 按时间筛选与分页。
- 点击查看原图，后端逐次鉴权。
- 管理员软删除和恢复操作。
- 家长列表、老师关系列表和邀请码管理。
- 与该学生有关的家庭会话列表和回复者标签。

普通老师只能查看有当前有效关系的学生；管理员和校区负责人沿用现有全局管理权限。

## 12. 错误处理与降级

- 下载或解密失败：不创建正式图片记录，删除临时文件并要求老师重传。
- 文件头异常、格式不支持或超限：拒绝归档并说明原因。
- 学生无法唯一识别：保留短期待确认任务，不猜测归属。
- 企业微信重复投递：返回既有处理结果，不重复保存文件或消息。
- 家长客服发送失败：保留消息和失败原因，允许安全重试。
- 模型不可用：家长消息仍保存；需要答复的消息转交老师，人工链路不被模型故障阻断。
- 老师关系在待回复期间失效：拒绝原老师发送，并重新路由当前主负责老师或交由管理员处理。
- 本机磁盘空间不足：停止接受新图片，保留原始消息处理失败状态并向老师提示，不写入指向缺失文件的数据库记录。

## 13. 测试策略

自动化测试覆盖：

- 学生、家长、老师关系的唯一性、有效期和权限范围。
- 老师越权上传、查看、删除图片或回复家长被拒绝。
- 精确学生 ID、唯一姓名、重名、无学生信息和无权限学生的处理。
- 单图、多图、纯图片、图文混排及渠道重复投递。
- 下载、解密、文件头、格式、大小限制、原子写入和临时文件清理。
- 邀请码过期、撤销、重复使用和不同监护人分别绑定。
- 多孩子选择和家长跨学生访问拦截。
- 回复者标签不可由家长消息或模型输出伪造。
- 渠道发送成功、失败和幂等重试。
- 模型故障时转人工流程继续工作。
- 学生档案图片接口和管理操作的服务端鉴权。

端到端验收路径：

老师上传图文图片 → 图片进入指定学生档案 → 家长通过邀请码绑定 → 家长查询图片 → 家长提问 → 机器人回复 → 转交老师 → 老师通过机器人回复 → 核对图片、关系、消息、标签和发送状态审计记录。

## 14. 分阶段实施与同批交付

该功能按三个可独立验证的阶段实现，但作为同一功能整体交付：

1. 学生关系和老师图片归档，包括学生档案图片区。
2. 家长微信客服入口、邀请码绑定和受限查询。
3. 统一家庭会话、机器人回复、老师中转回复和完整审计。

每个阶段都必须通过自身测试，第三阶段完成后执行完整端到端验收。

## 15. 非目标

首期不包括：

- 家长上传图片或文件。
- 视频、语音和任意文件归档。
- 云对象存储、CDN 和自动图片压缩。
- 短信验证码登录。
- 家长网页登录后台。
- 企业微信群聊或家长群机器人。
- 自动删除正式学生图片的固定保留期策略。

## 16. 验收标准

- 已授权老师能够在企业微信私聊中一次发送一张或多张图片并正确归档。
- 消息中有学生 ID 或唯一姓名时自动归档；缺失或重名时必须追问，不能误归档。
- 图片可在授权网页学生档案中查看，未授权请求返回拒绝结果。
- 普通微信家长可通过微信客服和有效邀请码绑定学生。
- 家长只能查询已绑定孩子的反馈、周报和图片。
- 家长能获得机器人回复，也能请求负责老师回复。
- 家长端每条系统回复明确显示“机器人回复”或真实老师姓名。
- 所有图片和消息处理具备幂等性，渠道重试不会创建重复记录。
- 模型故障不会丢失家长消息，也不会阻断老师人工回复。
- 数据库与本机媒体目录可一起备份并恢复出完整学生档案。
