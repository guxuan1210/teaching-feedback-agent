# 教学反馈数据采集 Demo 设计

日期：2026-09-05  
状态：已确认，待实施计划

## 1. 目标

交付一个可在单台电脑运行的教学反馈数据采集 Demo，用于尽快验证老师的真实填写流程并积累数据。

Demo 同时支持晚辅每日反馈和专项课反馈，数据持久保存到 SQLite。系统结构保留升级空间，后续增加账号、权限和在线部署时不重写核心数据与业务逻辑。

## 2. 成功标准

- 能新增、修改和停用老师、班级与学生。
- 能维护学生加入和退出班级的历史关系。
- 能创建一次课程场次，并按班级连续填写学生反馈。
- 晚辅和专项课分别展示对应的精简表单。
- 同一课程场次下，每名学生最多保存一条有效反馈。
- 历史反馈可以筛选、查看、修改和作废。
- 当前筛选结果可以导出为 Excel。
- 关闭并重新启动系统后，数据仍然存在。
- 错误输入不会写入数据库，保存失败不会清空老师已经填写的内容。

## 3. 首版范围

### 包含

1. 今日班级首页。
2. 班级批量填写工作台。
3. 晚辅每日反馈。
4. 专项课反馈。
5. 学生、班级、老师基础信息管理。
6. 学生入班与离班管理。
7. 历史记录筛选、修改和作废。
8. Excel 导出。
9. SQLite 本地持久化。

### 不包含

- 登录、账号与权限控制。
- 多人同时编辑。
- 家长端与家长签字。
- 入学测评录入。
- 自动月报、趋势分析和复杂图表。
- 手机原生应用。
- 正式公网部署。

## 4. 技术方案

- 后端：Python + FastAPI。
- 页面：Jinja2 服务端渲染，局部交互使用少量原生 JavaScript。
- 数据访问：SQLAlchemy。
- 数据库：SQLite。
- Excel 导出：openpyxl。
- 样式：本地静态 CSS，不依赖运行时外部网络。

选择该方案的原因：比 React 前后端分离更快交付，同时业务规则、数据库模型和查询逻辑可以在后续多人在线版中继续使用。SQLAlchemy 将 SQLite 访问集中在持久化模块内，未来确需 PostgreSQL 时可替换数据库适配实现。

## 5. 系统结构

```text
浏览器页面
   ↓ 表单提交／筛选／导出
FastAPI
   ├─ 基础信息模块
   ├─ 课程场次模块
   ├─ 反馈模块
   ├─ 历史查询模块
   └─ Excel 导出模块
        ↓
SQLAlchemy 持久化模块
        ↓
SQLite 本地数据库
```

所有数据库写入由业务模块执行，页面不直接拼接 SQL。每次保存反馈时，反馈主记录、指标选择和更新时间在同一个事务中提交。

## 6. 页面与操作流程

### 6.1 顶部导航

- 今日填写：默认首页。
- 历史记录：查询、修改和作废反馈。
- 基础信息：管理老师、班级、学生和入班关系。
- 导出数据：按当前筛选条件生成 Excel。

### 6.2 今日班级首页

首页默认显示当天日期和可用班级。老师先选择：

1. 日期。
2. 课程类型：晚辅或专项。
3. 班级。
4. 授课老师。
5. 专项课时填写课程名称。
6. 开始时间，默认当前时间。

首页同时显示当天已经创建的课程场次及完成进度。点击已有场次进入继续填写；点击“新建场次”始终创建新的课程场次，因此同一班级同一天可以有多节课。

### 6.3 班级批量工作台

- 左侧显示该班当前有效学生名单。
- 每名学生显示未填写、已填写或已作废状态。
- 右侧显示当前学生的反馈表单。
- 点击学生可以切换；未保存内容存在时先提示确认。
- 保存成功后标记当前学生为已填写，并自动进入下一名未填写学生。
- 所有学生完成后显示完成数量和返回首页入口。

## 7. 精简表单

### 7.1 晚辅每日反馈

必填：

- 知识掌握评分，1–5。
- 学习习惯评分，1–5。
- 心态与内驱力评分，1–5。

选填：

- 知识进步项、知识薄弱项。
- 习惯进步项、习惯薄弱项。
- 心态进步项、心态薄弱项。
- 补充备注。

页面展示以下指标分类：

- `daily_k_progress`
- `daily_k_weak`
- `daily_h_progress`
- `daily_h_weak`
- `daily_m_progress`
- `daily_m_weak`

### 7.2 专项课反馈

必填：

- 知识／技能评分，1–5。
- 课堂习惯评分，1–5。

选填：

- 已掌握项、薄弱项。
- 课堂优秀表现、待改进项。
- 补充备注。

页面展示以下指标分类：

- `special_k_progress`
- `special_k_weak`
- `special_h_progress`
- `special_h_weak`

现有85条指标继续保存在指标字典中。首版界面只展示上述核心分类，其他指标不删除，后续可重新开放。

## 8. 数据模型调整

以现有 `db/schema.sql` 为基础，Demo 增加和调整以下结构。

### 8.1 `class_session` 课程场次

- `session_id`：主键。
- `class_id`：班级。
- `teacher_id`：授课老师。
- `session_type`：`daily` 或 `special`。
- `course_name`：专项课程名称，晚辅可为空。
- `session_date`：课程日期，格式 `YYYY-MM-DD`。
- `start_time`：开始时间，格式 `HH:MM`。
- `status`：`active` 或 `cancelled`。
- `created_at`、`updated_at`。

课程场次定义“一课”。班级、老师、课程类型和日期不再在每名学生的反馈中重复解释。

### 8.2 `daily_feedback`

- 增加 `session_id` 外键。
- 增加统一的 `note`。
- 增加 `status`：`active` 或 `void`。
- 增加 `updated_at`。
- 增加唯一约束 `(session_id, student_id)`。
- 三项评分增加 1–5 的数据库约束。

### 8.3 `special_feedback`

- 增加 `session_id` 外键。
- 增加统一的 `note`。
- 增加 `status`：`active` 或 `void`。
- 增加 `updated_at`。
- 增加唯一约束 `(session_id, student_id)`。
- 两项评分增加 1–5 的数据库约束。

### 8.4 `enrollment`

- 移除阻止返班的 `UNIQUE(student_id, class_id)`。
- 同一学生在同一班级可以存在多段不重叠的入班历史。
- `start_date` 必填。
- `end_date` 为空表示当前在班；不为空时不得早于 `start_date`。
- Demo 业务逻辑阻止同一学生在同一班级出现两个同时有效的入班关系。

### 8.5 通用规则

- `class_type`、课程类型、反馈状态和启用状态使用数据库约束。
- 时间使用统一 ISO-8601 格式保存。
- 外键在每一个数据库连接上启用。
- 业务数据不硬删除；学生、老师和班级使用停用，反馈使用作废。

## 9. 历史记录

支持以下筛选条件：

- 开始日期和结束日期。
- 课程类型。
- 班级。
- 学生。
- 状态。

列表显示日期、课程类型、班级、学生、老师、评分摘要和状态。进入详情后可以修改反馈或将其作废。修改保存 `updated_at`；首版不实现完整的修改审批和不可变审计日志。

## 10. Excel 导出

导出范围与历史记录页面的当前筛选条件一致。生成一个 `.xlsx` 工作簿，包含：

1. 学生。
2. 班级。
3. 晚辅反馈。
4. 专项反馈。

反馈工作表包含课程日期、班级、学生、老师、各项评分、勾选指标、备注、状态、创建时间和修改时间。多个勾选项在单元格内使用中文分号合并为可读文本。

作废记录默认不导出；用户在筛选条件中明确选择“包含作废”时才导出。

## 11. 校验与异常处理

- 必填项缺失时不提交，并将页面定位到第一个错误字段。
- 评分超出1–5时，页面和数据库同时拒绝。
- 学生不在课程日期对应的有效班级名单中时拒绝保存。
- 同一场次同一学生重复提交时打开已有记录，不创建第二条。
- 写入失败时回滚整个事务，并保留页面中的已填写内容。
- Excel 导出失败只显示错误，不改变数据库。
- 应用启动时检查数据库文件、表结构版本和外键开关。

## 12. 测试策略

### 数据规则测试

- 评分边界：1和5成功，0和6失败。
- 同一场次同一学生不可重复。
- 已离班学生不能填写离班日期之后的反馈。
- 返班后可以在新有效期内填写。
- 反馈主记录和指标选择必须同时成功或同时回滚。
- 作废记录仍可查询，但默认不进入导出。

### 页面流程测试

- 从今日班级进入批量工作台。
- 保存后进入下一名未填写学生。
- 已填写学生重新打开时显示已有内容。
- 缺少必填项时显示明确错误且不清空输入。
- 历史筛选、修改和作废能够反映在列表中。

### 导出测试

- 工作簿包含四个预期工作表。
- 导出行数与筛选结果一致。
- 指标文案、中文文本和日期正确显示。
- 导出失败不修改任何业务数据。

## 13. 运行与升级

Demo 提供一个启动命令，在本机启动后自动打开或提示访问地址。数据库文件使用明确的 Demo 名称并位于项目数据目录中。

后续升级多人在线版时：

1. 保留 FastAPI 业务模块和 SQLAlchemy 数据模型。
2. 增加账号、角色、校区和教师班级授权。
3. 将 SQLite 适配实现替换为 PostgreSQL 适配实现。
4. 增加正式迁移、备份、审计和部署配置。
5. 根据使用反馈决定是否加入家长端、完整85项表单和月度分析。

## 14. Demo 的验证问题

本 Demo 重点回答：老师是否愿意使用班级批量工作台持续录入精简反馈，以及现有精简字段能否形成稳定、可导出的教学数据。

完成试用后，应记录老师填写耗时、跳过字段、常用指标、修改频率和导出使用方式，再决定哪些功能进入正式版本。
